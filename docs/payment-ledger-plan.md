# 決済情報の自動収集・集計 計画

方針: 手入力しない。使えるチャネルから拾い、1つの台帳に寄せて月次・カテゴリで見る。

日常の決済は **三井住友カード** と **PayPay** の2本。店の領収メールは補助。個人明細は Git に置かない。正本は Google スプレッドシート。

## 目的

- 何にいくら使ったかを、後から追わない
- 注文・請求・返金を同じ物差しで見る
- 配送メールや広告で件数を膨らませない
- 三井住友はメールで完結させ、PayPay だけ公式経路で埋める

## 2本柱

### 三井住友カード — メールで取れる（自動化しやすい）

実カードは **三井住友カード VISA（NL）**。

採用するメール:

- 差出人: `statement@vpass.ne.jp`
- 件名: `ご利用のお知らせ【三井住友カード】`
- 取れるもの: 利用日時、店名、金額、買物/取消

捨てる:

- `suguchan@vpass.ne.jp`（同じ利用の抽選通知。二重になる）
- `お支払い日のご案内`（金額なし）
- 認証コード

VポイントPay の利用メール（`info@prepaid.smbc-card.com`）は、NL 本体とは別ウォレット。使うなら別 `payment_method` で採る。

Cursor（3300円）や GamersGate（3464円）は、店メールが薄くてもこの通知で金額が付く。

### PayPay — メールでは取れない（ここが本丸）

PayPay 本体からのメールは認証・ログイン・本人確認だけで、決済明細は来ていない。公式のメール通知もキャンペーン寄りで、残高払いの1件ごとの領収には使えない。

消費者向けの取引 API も公開されていない。家計簿サービスとのライブ連携も、現状は公式 CSV 経由が前提。

アプリをスクレイピングする、通知を横取りする、ログインを自動化する、はやらない。壊れるし、口座ロックのリスクがある。

公式に残っている自動化の入口は次だけ。

**PayPay アプリの取引履歴 CSV（2025年2月〜）**

1. アプリ → 取引履歴 → 右上のダウンロード
2. 期間を指定して申請（一度に最大 365 日、直近約 2 年）
3. 準備完了の通知が来たら 24 時間以内に CSV を取る
4. 取引日時・出金/入金・取引先・取引方法・取引番号が載る

PayPayカード（プラスチック）の月次 CSV は別物。カード請求の検算用。残高・QR の明細はアプリ CSV のほう。

## PayPay をどう自動化するか

完全無人にはできない。公式が「申請してファイルを取る」までしか出していない。自動化は **取り出し以外** に寄せる。

| 案 | 手間 | 安定 | 採用 |
|---|---|---|---|
| A. 週1で CSV を Drive に置く。取り込みだけ自動 | 申請と保存だけ | 高い（公式） | **v1 の本線** |
| B. PayPay の支払い元を三井住友にする | 店頭の払い方を変える | 高い。店名はカード側の表記になる | 残高を使わない支出向けの補助 |
| C. 家計簿アプリ経由 | 別サービスが増える | CSV と同じ制約 | やらない（台帳は自前シート） |
| D. アプリ操作の自動ログイン / スクレイピング | 見かけ上ゼロ | 低い。規約・ロック | やらない |

### A の運用（推奨）

1. Drive にフォルダ `INN/paypay-csv/` を作る
2. 週1（または月末）にアプリで CSV を申請し、そのフォルダへ入れる
3. エージェントまたは後の Docker ジョブが新規 CSV だけ読む
4. `取引番号` を `source_id` にして追記。同じファイルを再投下しても増えない
5. 取り込み後の CSV は `imported/` へ移す

人手は「申請してファイルを置く」だけ。パース・重複排除・月次は自動。

### B の位置づけ

PayPay 画面で支払い方法を三井住友にすると、その利用は `statement@vpass.ne.jp` に乗る。完全自動に近づく。

ただし残高・ポイント払いは乗らない。チャージしてから払う使い方は A が必要。  
B は「これから残高を使わない支出」の補助であり、A の代わりにはしない。

## 店メールは補助

Amazon「注文済み」や Steam は、カード通知の店名が粗いときの補完に使う。  
集計の正は **三井住友の利用通知 + PayPay CSV**。店メールだけで足すと二重になる。

PayPayカードの「請求金額のお知らせ」と三井住友の支払日案内は、引落の検算行。明細合計には足さない。

## 台帳（正本）

- 名前: `INN 決済台帳`
- ID: `1Bd5h_VsQSlfEVCjxPl9l9TVOLqwkG5AVmAmN5EtvJDs`
- URL: https://docs.google.com/spreadsheets/d/1Bd5h_VsQSlfEVCjxPl9l9TVOLqwkG5AVmAmN5EtvJDs/edit

シート:

1. `transactions` … 1決済1行
2. `monthly` … 月 × 支払い手段 × カテゴリ
3. `sources` … 最終取込（Gmail / CSV ファイル名）

### transactions 列

| 列 | 意味 |
|---|---|
| source_id | SMCC は gmail message id。PayPay は取引番号 |
| booked_on | 発生日（JST） |
| merchant | 店名 |
| description | 取引内容 |
| category | 下記の固定語 |
| amount_jpy | 支出は正、取消・返金は負 |
| status | confirmed / pending / excluded |
| payment_method | `smcc_nl` / `vpoint_pay` / `paypay` / `paypay_card` |
| thread_id | メールのとき |
| collected_at | 取り込み日時 |
| notes | CSV ファイル名など |

### カテゴリ（v1 は固定）

`subscription` / `game` / `food` / `shopping` / `travel` / `other`

## 重複

1. 三井住友は `ご利用のお知らせ` のみ。すぐチャンは捨てる。取消は負の行。
2. PayPay は取引番号で一意。
3. 同じ支払いがカード通知と店メールの両方にいるときは、カード/CSV 側を正とし、店メールは紐付けメモだけ。
4. PayPay を三井住友で払った場合、SMCC 行と PayPay CSV 行が対になる。`payment_method` と突合キーで片方だけ `confirmed`。

## 段階

### v1

- 三井住友: Gmail から `statement@vpass.ne.jp` を取る
- PayPay: Drive の CSV を取り込む（申請は手作業）
- パーサと重複判定、エージェント用スキル
- 実データは Git に置かない

### v2

自宅 Docker で Gmail を定期取込。CSV フォルダも監視。申請そのものは公式が許すまで手作業のまま。

### v3

店メールで SMCC の「Visa加盟店」などを商品名に寄せる。任意。

## やらないこと

- PayPay / Vpass へのログイン自動化、スクレイピング
- プッシュ通知の傍受を本線にする
- 明細をリポジトリや INN 本文に保存する
- カード番号・口座番号の全文
- 家計簿 SaaS を正本にする

## 成功条件

- 三井住友の「ご利用のお知らせ」が手入力なしで台帳に載る
- PayPay は CSV を1回置くだけで追記され、再投下で増えない
- カード通知と店メールを二重に足さない
- すぐチャンメールで件数が増えない

## 残している判断

1. PayPay の申請頻度（週1か月末か）
2. これから残高払いを減らし、店頭を三井住友寄せにするか（B を併用するか）
3. VポイントPay を台帳に含めるか
